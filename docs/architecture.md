# Architecture

English Proofreader Pro is a skills-only plugin with an offline computation resource. It has no publisher-hosted service, API, MCP server, runtime backend, or third-party Python dependency. The host reads the plugin manifest and skill instructions and supplies the model and execution environment. The bundled helper does not create an executor in a host that lacks one.

## Repository roles

- `plugin.json` is the canonical plugin identity, version, UI metadata, and skill-only publication description.
- `skills/proofreader-pro/SKILL.md` defines proofreading, editing, rewriting, and drafting behavior. Keep it concise; the validator uses a 1 MiB UTF-8 compatibility ceiling, not the former 8,000-character project cap.
- `skills/proofreader-pro/agents/openai.yaml` contains skill UI metadata. The canonical skill name is `proofreader-pro`; the picker label is `ProofreaderPro`. The plugin label is `EnglishProofreaderPro`.
- `skills/proofreader-pro/scripts/text_metrics.py` owns deterministic measurements, whole-word budgets, final comparisons, and safe-fence/presentation data. It accepts bounded JSON data and uses only Python's standard library; it does not execute submitted text or contact a service.
- `assets/icon.webp`, `LICENSE`, and `PRIVACY.md` are runtime package assets and notices.
- `scripts/release.py` validates the runtime inputs and creates the distributable ZIP; it also stages a local compatibility copy for development.
- `tests/` contains synthetic behavior cases and deterministic packaging tests. Model/host acceptance checks are separate and manual.
- `scripts/evaluate.py` snapshots the skill, manifest, allowlisted helper bytes, selected fixtures, and runner context, then binds responses and manual assertion verdicts to those inputs. Exclusive creation protects existing evidence from concurrent writers. Resource-aware snapshots and records retain historical embedded helper text as data; validation never executes that historical text. Older records remain independently verifiable and cannot accept a changed resource-assisted candidate.
- `scripts/capture_protocol.py` gates CLI output acceptance on real source/final measurement commands, returned structured data, fresh challenges, and exact output hashes. The controller owns protected plans, collected events, and accepted copies.
- `scripts/check_capture_evidence.py` checks the retained execution evidence, accepted outputs, snapshots, and graded response strings portably in CI. Recorded host paths are inert identity metadata, not commands to run on the CI machine. The gate cannot replace an absent generator execution with a later reviewer recount.

## Behavior boundaries

The skill defaults to minimal edits and preservation of meaning, voice, pronouns, and formatting. Text supplied for processing—including quoted or fenced instructions—is source material, not authority to change the task. For supplied text, the skill reports actual changes; drafting from scratch does not use a Changes list. Literal Markdown and nested fences must remain safe to copy. These instructions are the product's core behavior and should not be changed incidentally during packaging or documentation work.

The skill describes desired behavior; it cannot guarantee identical output across models, hosts, or contexts. The test suite checks local deterministic properties and packaging, not universal model quality.

The editing workflow orders five checks: separate directions from the complete source, calculate shortening budgets or inventory drafting facts, compose text, verify counts and every edit, then construct a safe copyable block. All counting requires programmatic tools, including internal shortening checks. Source may be passed to those tools only as inert data, never executed or used to authorize browsing or app actions. Changes quotations use display-only Markdown escaping inside their outer bold markers so literal source syntax remains visible; those escapes never belong in the copyable text or edit ledger. The final check includes quoted spans in Changes explanations. These are instructions executed by the host model; the package does not supply a runtime tool sandbox or force code-block controls. Historical simulations and pending acceptance are recorded in [validation evidence](../tests/RESULTS.md).

Fenced/code-example payloads remain literal unless the user explicitly asks for edits inside them. Preserve their fence delimiters and other formatting in either case. Ordinary text editing, source-command isolation, pronouns, and Changes-list requirements still apply. See [host compatibility](host-compatibility.md) for model recommendations and capability boundaries.

## Evaluation and execution evidence

Evaluation snapshot schema **2** preserves the exact allowlisted helper at `skills/proofreader-pro/scripts/text_metrics.py` in a `resources` entry containing its path, UTF-8 text, SHA-256, and byte count. Record schema **3** includes the resource path/hash map in `source_binding.resources`, alongside the skill, manifest, and frozen runner context. This keeps physical source bytes, including CRLF, tied to the reviewed outputs. The evaluator reads resource text as data; it does not import or execute preserved historical code.

New records require resource-aware snapshots. A missing, changed, invalid, or symlinked current helper prevents current acceptance, while the embedded original bytes keep historical evidence independently verifiable. Snapshot schema 1 and record schemas 1/2 remain historical formats; they cannot accept this resource-assisted candidate. Input changes require new snapshots and captures, never revised historical responses or substituted passes.

The CLI capture protocol adds a separate execution boundary. A trusted controller prepares a fresh challenge and protected plan, collects the CLI's actual event stream, and accepts a provisional candidate only after successful source/final measurement commands return data for its exact bytes. Those commands execute the reviewed shipped helper. Controller files must be outside the generator's actual writable scope; a pathname convention alone is not an operating-system boundary. Permission and hook requirements belong to the real launch configuration and must be checked before a run.

The portable CI checker binds plans, events, runtime receipts, accepted bytes, current resource-aware snapshots, and graded response strings. Recorded original host paths are inert metadata. The checker uses only the reviewed current local helper for its integrity recount; that recount cannot supply an absent generator tool event. Its trust in the original collector and recorded interpreter identity is not cross-platform binary attestation, proof of hidden reasoning order, semantic grading, or native host acceptance. See [testing](../tests/README.md#cli-execution-acceptance) for the controller and panel contract.

The earlier `count-routing` panel remains historical, including its [failed generation-protocol review](../tests/trials/count-routing-cli-protocol-review-2026-11-25.json). Capture 3's final measurement claims lack corresponding execution events even though its visible-output assertions passed. The separate current [V4 panel](../tests/trials/resource-execution-v4-panel-2026-11-25.json) passes actual source/final execution checks for three captures and 411 independently reviewed assertions. It does not rewrite the earlier failure or establish native acceptance; native testing remains incomplete.

## Distribution

Run `python3 scripts/release.py validate` and `python3 scripts/release.py build`. The resulting ZIP is an allowlisted seven-file runtime package: `plugin.json`, the skill, its UI metadata, its counting helper, the icon, `LICENSE`, and `PRIVACY.md`. Repository history, tests, screenshots, development catalog, and repository build/evaluation scripts are excluded. `dist/local-plugin/` is a development staging copy, not the public release artifact.

The validator rejects duplicate JSON keys, invalid semantic versions, and empty skill bodies. The file ceiling is measured in actual UTF-8 bytes, including physical CRLF bytes; metadata retains its character limits. Metadata uses a deliberately narrow YAML subset: unique keys at fixed indentation levels with string scalars; plain strings, JSON-compatible double-quoted strings, and single-quoted strings with doubled apostrophes. Raw YAML source must use the printable character range, including comments and ignored lines; supported quoted escape sequences are parsed separately. Collections, multiline scalars, implicit typed values, and undeclared fields are rejected. Quote values that resemble YAML booleans or numbers.

Icon validation checks the WebP container, chunk bounds, frame headers, dimensions, and a 5 MiB size limit using the standard library. CI additionally decodes the image with libwebp's `dwebp`; compressed pixel decoding is separate from the offline structural checks. The decoder is a CI asset-verification dependency, not a dependency of the plugin or local archive builder.

Build captures all seven runtime files into one immutable byte snapshot, validates that snapshot, and generates both the ZIP and staging copy from it. Helper validation checks UTF-8, size, and Python syntax without executing the code. Output verification compares every payload byte with the validated snapshot, including the generated legacy manifest. Source edits after capture cannot enter either output. Capture reads the files sequentially; it is not an atomic repository revision or an operating-system confinement boundary.

Build prepares and verifies temporary outputs before publication. The old ZIP stays at its final path until one atomic replacement; a failed promotion rolls back local staging or reports the preserved backup path if restoration fails. Run one build at a time from a stable, reviewed source tree. ZIP replacement and staging replacement are separate filesystem operations, so an interrupted process still requires checking outputs before distribution.

Preflight recognizes only the two known runtime files under each retired staging path, `skills/proofread/` and `skills/english-proofreader-pro/`, so previous generated builds can be replaced. Unknown files, symlinks, and non-regular entries there still block replacement. Newly prepared staging trees and ZIPs use only the current seven-file allowlist; retired skills are never bundled as aliases.
